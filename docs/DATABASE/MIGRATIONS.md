# Migrations Policy

## Official baseline

| Migration | Purpose |
|-----------|---------|
| `20260520215307_InitialEnterpriseBaseline` | Full enterprise schema: SaaS, billing, ERP, Wave 1 `company_id`, RLS SQL |

Only **one** migration in chain until production deploy. New schema work:

```bash
cd backend/src/ERP.Infrastructure
dotnet ef migrations add <DescriptiveName> --startup-project ../ERP.API/ERP.API.csproj
```

Every add must produce:

- `{timestamp}_{Name}.cs`
- `{timestamp}_{Name}.Designer.cs`
- Updated `ErpDbContextModelSnapshot.cs`

**Never** hand-author migration files without EF tooling.

## Verify model sync

```bash
dotnet ef migrations has-pending-model-changes --startup-project ../ERP.API/ERP.API.csproj
```

Must return **no pending changes** before merge.

## Apply

```bash
dotnet ef database update --startup-project ../ERP.API/ERP.API.csproj
```

Or rely on `Database.MigrateAsync()` at API startup.

## New developer database

```sql
DROP SCHEMA public CASCADE;
CREATE SCHEMA public;
GRANT ALL ON SCHEMA public TO postgres;
GRANT ALL ON SCHEMA public TO public;
```

Then `dotnet ef database update`.

## Pre-production squash

While no production DB depends on history:

1. Remove incremental migrations
2. Regenerate single `InitialEnterpriseBaseline` from current model
3. Re-append RLS SQL (not generated by EF)
4. Drop dev DB and re-apply

## Production rules

- Forward-only `database update`
- Backup before apply
- Never `DROP SCHEMA` on shared environments
- Plan data backfills in migration `Up()` with idempotent SQL

## Naming in schema

- Index/FK suffix: `_subscriber_` not `_tenant_`
- SaaS billing: `saas_billing_*`, `subscriber_billing_accounts`
- ERP SRI settings: `billing_settings` (not SaaS billing)
